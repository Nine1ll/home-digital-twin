# 설계 설명

## 현실과 디지털 상태의 연결

이 버전의 트윈은 수동 기록으로 동기화됩니다. 실제 집을 자동 관측하지 않으므로 사용자가 이동·소비·폐기를 기록해야 합니다. 공간은 각 부모 안에서 20×20 상대 좌표를 갖습니다. 겹침을 허용하며 건축 치수나 충돌 검증을 의미하지 않습니다. 2D 표현만으로 먼저 ‘등록한 물건을 다시 찾는가’를 검증합니다.

## 모델을 나눈 이유

| 모델 | 책임 | 원본과의 차이 |
|---|---|---|
| Household | 집과 공동 설정 | 실제 초대 가입, 변경 가능한 임박 기준 |
| User | 인증과 가구 소속 | 한 사용자 한 가구, 가입 시 합류 선택 |
| Location | 방/가구/수납 칸과 상대 배치 | 좌표·크기·종류·순환 방지 |
| Product | 상품 정체성, 바코드, 구매 기준 | 같은 상품의 여러 재고를 연결 |
| Batch | 상품+위치+유통기한별 수량 | 유통기한 없음은 빈 문자열로 고유 제약 적용 |
| Activity | 재고 변화를 설명하는 불변 기록 | 당시 이름/경로 보존, 폐기/정정/이동 분리 |

상품명은 공백과 대소문자를 정규화하여 같은 가구 안에서 중복을 막습니다. 동일 상품명에 다른 규격이 필요하면 이름에 규격을 넣으세요. 현재 모델은 상품 하나에 바코드 하나, 정수 수량과 하나의 단위만 지원합니다.

## 재고 불변 조건

- 수량은 0 이상입니다. DB CHECK와 요청 검증을 함께 사용합니다.
- 부분 이동은 출발 재고 감소 + 도착 배치 합산 + 이동 이력을 같은 트랜잭션으로 저장합니다.
- 낙관적 잠금: `version`이 읽은 값과 같은 경우만 UPDATE합니다. 동시에 수정됐으면 409로 다시 확인하게 합니다.
- 같은 배치의 동시 첫 등록은 고유 제약이 충돌을 감지합니다. 자동 재시도하지 않습니다.
- 빈 재고도 보존하여 Activity의 참조가 끊어지지 않게 합니다.
- 활동 이력에 수정/삭제 API는 없습니다. DB 관리자까지 수정 불가능한 감사 저장소는 아닙니다.
- 이름이나 위치 이름이 바뀌어도 과거 이력의 스냅샷은 바뀌지 않습니다.
- 물건/이력이 연결된 위치는 삭제를 막습니다. 향후 보관 종료(archive)를 별도 설계할 수 있습니다.

## 예측과 학습 누수

1. 최초 재고 기록부터 최근 최대 90일 중 완료된 날짜만 관측합니다. 오늘은 부분 관측이라 학습하지 않습니다.
2. `consume`만 사용량으로 집계합니다. `discard`, `move`, `adjust`는 제외합니다.
3. 완료 7일 미만 또는 소비가 있는 날 3일 미만이면 추정하지 않습니다.
4. 기본은 최근 14일 평균입니다.
5. 28일 이상, 소비일 8일 이상이면 Ridge 회귀를 후보로 학습합니다. 특성은 시간 추세와 요일의 sin/cos입니다.
6. 마지막 7일을 검증용으로 떼어 ML과 평균 기준선의 MAE를 비교합니다. ML이 개선할 때만 전체 관측으로 재학습해 다음 7일 일평균을 계산합니다.
7. 만료 재고를 제외한 사용 가능 수량 / 일평균 소비량으로 대략적인 소진일을 구합니다.

계산은 `ml/forecast.py`(예측 서버)에 있습니다. 예측일은 확률 구간이나 보장된 소진일이 아닙니다. 기록하지 않은 날은 사용량 0으로 처리하므로 기록 누락이 많으면 편향됩니다. 하루 0.001개 미만의 작은 값은 표시 반올림의 영향을 받습니다. 실제 재고 실사와 기록 습관이 모델보다 먼저입니다. 상품별 데이터가 작으므로 이 구조는 ML 학습 과정을 이해하는 참고 구현입니다.

## 프론트와 백엔드 연결

빌드 도구를 도입하기 전에 익숙한 HTML/CSS/JS와 FastAPI를 유지했습니다. `/api`는 API, `/`는 정적 프론트입니다. API 주소는 `frontend/config.js`의 `API_BASE` 한 곳에서 정하며, 비워 두면 같은 주소의 `/api`를 씁니다.

폼은 위치 조회가 끝날 때까지 빈 화면을 보여 주지 않습니다. 초기 상태를 한 번 불러온 뒤 화면을 그립니다. 네트워크 요청에는 제한 시간이 있으며 저장 시간 초과 시 중복 재시도 전에 목록을 확인하도록 안내합니다. 현재 자동 동기화/WebSocket은 없으며 다른 가족의 변경은 새로고침으로 확인합니다.

## 서버 분리

구조를 배우기 위해 한 프로세스였던 서비스를 세 서버로 나눴습니다. 같은 코드로 **한 서버**(개발)와 **세 서버**(compose) 모두 실행됩니다.

```
브라우저 ──▶ web (nginx)  : 화면 파일 제공, /api 요청을 api로 넘김(리버스 프록시)
               │
               ▼
             api (FastAPI) : 인증, 재고, 공간, 알림, 푸시. DB를 가진 유일한 서버
               │  POST /forecast  (X-Internal-Token)
               ▼
             ml (FastAPI)  : 소비 예측 계산만. DB 없음, scikit-learn은 여기만
```

### 무엇을 기준으로 나눴나

| 서버 | 책임 | 가진 것 | 갖지 않은 것 |
|---|---|---|---|
| web | 정적 파일, 프록시 | `frontend/`, `deploy/nginx.conf` | 비밀값, DB |
| api | 규칙과 데이터의 주인 | DB, `SECRET_KEY`, 푸시 키 | ML 라이브러리 |
| ml | 계산 | `ML_TOKEN` | DB, 사용자 정보, 다른 비밀값 |

- **DB는 api만 가집니다.** ml이 DB를 직접 읽으면 테이블을 바꿀 때 두 서버를 같이 바꿔야 해서, 서버를 나눈 의미가 사라집니다(분산 모놀리스). ml은 “이벤트 목록 → 예측”만 아는 순수 계산 서버라서 입력만 같으면 언제든 같은 답을 냅니다.
- **최소 권한**: compose에서 ml에는 `ML_TOKEN`만 넘깁니다. ml이 뚫려도 사용자 비밀번호 해시나 JWT 서명 키는 없습니다.

### 서버 사이의 약속(계약)

```http
POST /forecast
X-Internal-Token: <ML_TOKEN>

{"today": "2026-09-30",
 "products": {"12": [{"created_at": "2026-09-01T08:00:00", "action": "consume", "quantity": 1}]}}

→ {"12": {"method": "moving_average", "daily_rate": 0.5, "days_observed": 29, "reason": "…", "validation_mae": null}}
```

- **한 번에 묶어서 호출**합니다. 상품마다 호출하면 상품이 50개일 때 화면 한 번에 요청이 50번(N+1) 나갑니다. `tests/test_ml.py`가 “화면당 1회”를 검증합니다.
- `today`를 api가 정해 보냅니다. 두 서버의 시계가 달라도 같은 날 기준으로 계산됩니다.
- 계약을 바꾸면(필드 추가·이름 변경) 두 서버를 함께 배포해야 합니다. 필드를 **추가**만 하면 옛 서버와도 호환됩니다.

### ml이 죽으면

분리의 대가는 “서버 하나가 없을 때도 전체가 동작해야 한다”는 설계 부담입니다.

| 상황 | 동작 |
|---|---|
| ml 꺼짐·연결 거부 | 즉시 실패 → 예측만 ‘예측 일시 중단’, 나머지 정상 |
| ml 느림 | 3초 뒤 포기(`timeout=3`) → 위와 같음 |
| 토큰 불일치 | 401 → 위와 같음 (로그에서 원인 확인) |
| ml 복구 | 다음 요청부터 자동 정상 |

유통기한 알림, 최소 재고 기준 장보기, 푸시는 예측 없이도 계산되므로 계속 동작합니다. 핵심 기능이 부가 기능(예측)에 묶이지 않게 한 것입니다.

### 서비스 사이 인증

ml은 인터넷에 공개하지 않지만(compose 내부망, Render 비공개 서비스) 한 겹 더 확인합니다. 두 서버가 같은 `ML_TOKEN`을 갖고, ml은 `secrets.compare_digest`로 비교합니다(타이밍 공격 방지). 운영 환경에서 비어 있으면 ml이 시작하지 않습니다.

### 얻은 것과 잃은 것 (측정값)

| | 한 서버 | 분리 후 |
|---|---|---|
| API 프로세스 메모리 | 약 143MB | 약 90MB (scikit-learn 제외) |
| ML 프로세스 메모리 | – | 약 133MB |
| 알림 화면 응답 | 약 7ms | 내부망 호출 1회 추가 |
| 배포 단위 | 1 | 3 (web, api, ml) |
| 장애 지점 | 1 | 3 → 대비책 필요 |

지금 규모(가족 1집, 상품 수십 개)에서는 성능 이득이 없습니다. 이 분리는 **구조를 익히고**, 나중에 무거운 모델(예: GPU가 필요한 사진 인식, 여러 집 데이터로 학습)을 ml 쪽에만 붙일 수 있게 하려는 것입니다.
