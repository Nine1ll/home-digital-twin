# 사용자 피드백 반영

## 직접 사용해 보기

1. 가입할 때 표시 이름을 입력합니다. 기존 계정은 설정에서 ‘가족’을 ‘아빠’, ‘딸’ 등으로 바꿉니다. 이메일은 로그인에 사용합니다.
2. 공간이 없는 집에서 **집 프리셋**으로 원룸·1.5룸·투룸·스리룸·방 3/화장실 1·방 3/화장실 2 중 선택합니다. 기본 가구는 선택 사항이며 실제 도면을 재현한 것이 아닌 편집 가능한 시작 배치입니다. 기존 집은 덮어쓰지 않습니다.
3. 주방 안에서 **수납칸 일괄 추가**를 누르면 상부장 1~4처럼 생성됩니다. 공간 설정의 **하위 공간까지 복제**는 형제 공간으로 구조만 복사합니다. 재고는 복제하지 않으며, 복제본은 원본과 겹치므로 배치 편집으로 옮깁니다.
4. 우유 등록 시 소비 관리를 **대략적인 잔량**으로 선택합니다. 기존 우유는 알림 → 상품·구매 기준 수정에서 변경합니다. 수량은 팩 수, 잔량은 개봉한 한 팩의 상태입니다.
5. 소비 버튼에서 한 포장 개봉 → 한 컵/한 번 사용 → 절반쯤/조금 남음 → 다 씀을 기록합니다. 한 컵은 사용 이벤트만 남기고 임의로 200mL 등을 빼지 않습니다. ‘다 씀’만 포장 수량을 1 줄입니다. 폐기는 소비 예측에서 제외됩니다.

같은 상품·위치·유통기한 묶음당 동시에 한 포장만 개봉하는 MVP입니다. 개봉 중인 묶음의 일반 이동·정정은 차단됩니다. 여러 포장 동시 개봉 및 개봉 포장 이동은 후속 확장 범위입니다. 개봉 후 보관 가능 기간은 상품마다 달라 자동으로 유통기한을 바꾸지 않습니다.

## 예측의 의미

개수형 상품은 기존 평균/Ridge 검증 방식을 유지합니다. 잔량형 상품은 ‘개봉 → 다 씀’을 완료한 3포장 이상부터 최근 최대 10포장의 평균 사용 기간을 사용합니다. 개봉 후 지난 기간과 미개봉 수량을 고려한 대략적인 소진 예상이며, 컵을 부피로 변환하거나 잔량 단계에 임의 비율을 부여하지 않습니다. 사용 주기 변화나 동시 사용에는 오차가 있습니다. ‘조금 남음 + 미개봉 여분 없음’은 기록이 부족해도 구매 안내를 표시합니다.

## 바코드

GTIN-8/12/13/14 길이와 검증 숫자를 확인합니다. 앞자리로 상품명이나 제조국을 추측하지 않습니다. 우리집에 저장한 상품을 먼저 조회하고, 없으면 Open Food Facts를 조회합니다. 번호 오류, 상품 없음, 조회 서버 연결 실패를 구분합니다. 상품이 없으면 이름 또는 사진 제안을 확인해 등록하면 그 바코드를 우리집에서 기억합니다. 사진 인식에 성공해도 상품명과 유통기한은 사용자가 확인해야 합니다.

한국 상품 데이터베이스를 새로 연결한 것은 아닙니다. 사진 인식은 기존 OLLAMA_URL 설정이 필요합니다. 별도 국내 데이터 공급 계약/API 키 없이 국내 모든 상품을 인식한다고 보장하지 않습니다. 기존 데이터에 잘못된 검증 숫자로 저장된 바코드는 새 등록·조회에서 거절될 수 있습니다.

## 데이터 변경과 운영 로그

서버 시작 시 기존 테이블에 display_name, consumption_mode, remaining_level, opened_at 열만 추가합니다. 기존 행·수량·이력은 유지하며, 기존 상품은 개수형으로 시작합니다. SQLite 기존 스키마의 보존 및 재실행을 테스트했습니다. PostgreSQL용 DDL과 advisory lock을 포함하지만 실제 PostgreSQL 실행 검증은 하지 않았습니다. 운영 DB를 백업한 뒤 배포하세요.

고객 화면과 HTTP API에서 전체 활동 기록을 제거했습니다. 기록은 예측 및 문제 확인을 위해 DB에 남고, DB 접근 권한을 가진 운영자만 CLI로 조회합니다. 이메일 대신 표시 이름과 내부 사용자 ID를 출력합니다. 별도 관리자 웹 화면은 만들지 않았습니다.

```bash
python -m backend.audit --household-id 1 --limit 30
```

## 학습 순서

`models.py` → `schemas.py` → `main.py`의 portion/space-group/preset 처리 → `frontend/app.js`의 해당 다이얼로그 → `tests/test_feedback.py` 순서로 읽으면 데이터, API, 화면, 검증이 어떻게 연결되는지 볼 수 있습니다. `migrations.py`는 기존 DB에 모델 변경을 전달하는 이유를 보여 줍니다.
